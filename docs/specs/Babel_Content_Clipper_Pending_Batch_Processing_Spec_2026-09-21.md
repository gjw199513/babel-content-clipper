# Babel Content Clipper：待办统一处理规范说明书

> 独立功能 Spec，不并入既有总体 PRD/访谈 Spec。
> 来源：用户对资料库中多条“待处理”记录提出的统一处理要求，以及既有 PRD 的批量领取与逐项回写规则。
> 创建时间：2026-09-21 CST
> 状态：COMPLETE；实现与验证状态在本文单独维护。

## 背景与缺口核查

既有产品规范已经定义：用户可以要求 Agent “把今天标记的这些片段处理一下”；`claim_records` 支持一次提交多个 `jobId`，并逐项返回 `accepted`、`already_claimed`、`not_eligible` 等结果；批次内每条记录保持独立，单条失败不撤销其他结果。

当前缺口不在 Core 或 MCP 的领取能力。首个已发布资料库页面只接入了单条记录的“复制任务说明”，没有提供面向全部待办或当前筛选范围的批次交接入口。因此这不是底层批量接口被删除，而是原规划未完整接到资料库 UI。

## 需求 (Requirements)

### 功能需求

| 编号 | 需求 |
|---|---|
| PB-01 | 资料库提供“统一处理待办”入口，用户不需要逐条打开记录。 |
| PB-02 | 默认批次范围为当前来源、日期与搜索筛选下的全部真实 `pending` Job；清空筛选即代表全部待办。当前“全部/历史”等展示标签不把非 pending 状态带入批次。 |
| PB-03 | 点击入口先遍历所有分页并冻结 `captureId`/`jobId` 快照；不得只取当前已显示的第一页。 |
| PB-04 | 资料库生成一份批次任务说明，明确这是一条执行授权，无需 Agent 再逐项询问；批次形成后新增记录不自动加入。 |
| PB-05 | 批次说明只包含可信 Capture/Job ID 和执行规则，不复制标题、正文、评论、私有 URL、Cookie、claim token 或其他网页数据。 |
| PB-06 | 复制批次说明本身不领取、不下载、不改变 Job 状态。用户将说明交给已连接 Agent 后，由 Agent 调用 MCP 执行。 |
| PB-07 | MCP 发布 `pending_batch_processing` 机器可读/人类可读指南，要求 Agent 遍历分页、冻结范围并分批原子领取。 |
| PB-08 | 单次 `claim_records` 最多 200 个 `jobId`；更大批次拆成多波。只处理 `accepted`，其余逐项跳过并汇总。 |
| PB-09 | 每条 accepted Job 独立读取、输出、心跳、验证与终态回写；一条失败不回滚其他成功项，不合并原始记录。 |
| PB-10 | `processing`、`completed`、`failed`、仅收藏、未封存或中断记录不进入普通待办批次。失败 Job 不自动重处理，完成后不自动清理。 |
| PB-11 | 每条 Job 按自己的实际输出要求处理；只有明确需要视频文字且现有文字不足时才进入 `video_text_extraction` 指南。 |
| PB-12 | 批次结束后 Agent 汇总 completed、failed、skipped 和状态不确定项，但每条 Job 的持久化 Result 仍是终态事实。 |

### 用户故事

- 作为积累了多条待办的用户，我只需一次复制统一处理说明并交给 Agent，不再逐条点开记录。
- 作为只想处理某个来源或今天记录的用户，我可以先使用现有筛选，再生成该范围的待办批次。
- 作为更换 Agent 或会话的用户，我可以再次按当前真实待办生成新快照；已经领取或终态的项目不会重复进入。
- 作为需要混合处理文字、图片和视频的用户，我允许同一批次内使用不同处理指南，但要求每条结果仍可单独追溯。

### 验收标准

- 创建至少两条 pending、一条 processing、一条 completed、一条 failed 和一条仅收藏记录；批次说明只包含两条 pending 的 Capture/Job ID。
- 待办超过一页时，批次说明包含后续页符合筛选的记录，不把第一页当作全部。
- 使用来源、日期或搜索筛选后，批次快照只包含筛选范围内的 pending Job；清空筛选后包含全部 pending。
- 点击“复制统一处理说明”后，所有 Job 状态保持不变。
- 说明中不包含页面正文、标题、评论、私有 URL、Cookie 或 claim token。
- Agent 对超过 200 项的快照拆分领取；每项只在 disposition 为 accepted 时执行。
- 批次中一项失败时，其他项仍可完成并分别收到 `ack.persisted=true`；失败不自动回到 pending。
- 两个 Agent 同时处理同一批次时，同一 Job 仍只能有一个 accepted claim。
- 新 Job 在快照复制后创建时，不进入这次说明；用户可重新生成下一批。
- 资料库在窄屏和多语言界面下仍能显示批次入口，不遮挡现有筛选、维护和记录详情。

## 约束 (Constraints)

### 架构约束

- 浏览器扩展无法通用地启动任意 MCP 客户端中的 Agent。首版入口因此生成一次性、可审计的批次任务说明；真正执行由用户已经连接的 Agent 完成。
- 现有 `list_records`、`get_record`、`claim_records`、心跳和 `commit_result` 继续作为执行接口，不新增第二套任务数据库或自动调度器。
- 批次是授权与编排快照，不是新的 Capture/Job/Result 实体。

### 安全约束

- 网页内容均为不可信数据，不能进入可信批次控制字段。
- 批次说明不携带私密取源上下文；来源地址只能在 accepted claim 下通过现有受控工具取得。
- 不以批量为由放宽安装、文件系统、登录态、下载、模型或浏览器自动化边界。

### 性能与可靠性约束

- UI 必须持续读取 `nextCursor`，但只收集轻量列表字段，不整批读取附件或完整正文。
- MCP 单次领取维持现有 200 项上限。Agent 可按资源情况分波执行，并对长任务逐项维持心跳。
- 批次汇总不能代替逐项持久化 ACK，也不能在部分成功时伪报“全部完成”。

## 决策 (Decisions)

| 编号 | 决策 | 理由 |
|---|---|---|
| PD-01 | 使用“当前筛选范围 + pending 状态”作为批次默认范围。 | 同时满足全部待办和按来源/日期处理，不需要逐项勾选。 |
| PD-02 | UI 生成固定 ID 快照，而不是只复制“处理全部”一句自然语言。 | 防止分页遗漏、后续新增意外加入，并形成明确授权边界。 |
| PD-03 | 批次入口只复制说明，不在扩展内直接 claim。 | 保持标准 MCP/Agent 架构；复制失败不会留下无人处理的占用。 |
| PD-04 | MCP 增加只读批次指南 topic/resource，不新增自动执行工具。 | 底层 list/claim/commit 已支持批量，缺的是 Agent 编排指导。 |
| PD-05 | 待处理详情不再对 pending/processing 显示“重新处理”。 | 重新处理只适用于终态 Job，避免用户把它误解为“开始处理”。 |
| PD-06 | 不默认增加跨 Job 并发数。 | 不同 Agent 的 CPU、磁盘和 ASR 成本不同；统一入口不等于无限并发。 |

## 实现与验证记录

截至 2026-09-21，本 Spec 已映射到：

- 资料库“复制统一处理说明”入口，以及 current-filter pending 快照生成逻辑；
- `pending_batch_processing` 结构化 MCP 指南和 Markdown 资源；
- pending/processing 详情隐藏“重新处理”，仅终态记录显示该动作；
- 分页循环、重复 Job、防游标循环的单元测试；
- MCP stdio 指南工具/资源测试；
- 真实扩展页面批次复制回归，确认两条 pending 被纳入、completed 被排除、复制不领取、不可信正文不进入说明；
- 五语言浏览器响应式回归、TypeScript 类型检查、LSP、全量单元测试和包完整性检查。

这些证据确认当前实现与本 Spec 的静态、协议和本机 Chromium 行为一致；它们不等于任意第三方 Agent 客户端都会自动响应剪贴板内容。用户仍需把说明交给已连接 Agent，或直接对 Agent 明确说“处理全部待办”。

### Q1：是否支持一次处理全部待办

**用户要求**：资料库中都是待处理记录，不应要求逐条点击，希望统一处理；用户记得此前规划 Spec 已包含该能力。

**代码与文档核查**：原 PRD 和 Core/MCP 已有批量语义及接口，资料库 UI 只有单条任务说明。结论是 UI/Agent 指导的实现缺口，不是底层功能被删除。

### Q2：是否写入原有 Spec

**用户要求**：本要求写在单独的 Spec 文档，不和之前文档混在一起。
